# AI Investment Research Agent — продакшен

Автономний агент, який сам, за розкладом, збирає макроекономічні дані,
звітність компаній, новини й офіційну статистику, порівнює факт із
ринковими очікуваннями, прогнозує наступні значення показників і
надсилає в Telegram короткі звіти та списки активів, варті уваги.

Працює без оператора: `docker compose up -d` піднімає базу, застосунок
і планувальник — далі **54 джоби** виконуються самі за розкладом
(часовий пояс `Europe/Kyiv`). Ручні команди потрібні лише для
розгортання й розбору збоїв.

```
┌─ ЗБІР ──────────────┐   ┌─ АНАЛІЗ ─────────────┐   ┌─ ЗВІТИ ────────┐
│ макро (FRED/ECB/    │   │ прогноз показника    │   │                │
│   BOJ/e-Stat/BLS)   │   │ факт vs очікування   │   │                │
│ акції (SEC EDGAR,   │──▶│ скринінг S&P 500     │──▶│   Telegram     │
│   Twelve Data)      │   │ крипто-скринінг      │   │                │
│ крипта (Binance/    │   │ синтез ринку (ШІ)    │   │                │
│   Bybit/OKX/Gecko)  │   │ синтез ставки ЦБ     │   │                │
│ новини (17 RSS +    │   │ пошук новачків       │   │                │
│   GDELT)            │   │ список для торгів    │   │                │
└─────────────────────┘   └──────────────────────┘   └────────────────┘
          │                          │                        │
          └──────── PostgreSQL + TimescaleDB ─────────────────┘
                 (одна база: часові ряди + реляційні дані)
```

## Що агент робить

### Збирає

| Домен | Джерела | Де |
|---|---|---|
| Макро | FRED (США), ECB Data Portal (єврозона), BOJ + e-Stat (Японія), BLS (звірка з FRED) | `data-ingestion/macro/` |
| Акції | SEC EDGAR (фундаментал, XBRL), Twelve Data + Yahoo Chart (ціни/обсяг) | `data-ingestion/companies/`, `quotes/` |
| Звіти | SEC EDGAR 10-K/10-Q — **текст** MD&A і Risk Factors, не цифри | `data-ingestion/reports/` |
| Крипта (спот) | Binance public API, CoinGecko | `data-ingestion/crypto/` |
| Крипта (ф'ючерси) | Binance + Bybit + OKX Futures | `data-ingestion/crypto/` |
| Товари | TradingEconomics (там, де FRED не дає денної свіжості) | `data-ingestion/commodities/` |
| Новини | 17 RSS-фідів (9 геополітичних, 8 ринкових) + GDELT по watchlist | `data-ingestion/news/` |
| Календар релізів | FRED (офіційна дата) + ForexFactory-фід (точний час, impact, forecast) | `monitoring/` |

### Аналізує

- **Прогноз наступного значення показника.** Метод обирається
  **за показником** (`analysis/forecasting/method_selector.py`) на
  підставі вердиктів бектесту в БД: ШІ працює на 8 показниках із 19,
  решта пишуть naive **без виклику LLM** — бо на них ШІ зміряно гірший
  за безкоштовне «нічого не змінилось».
- **Факт vs ринкове очікування** після кожного релізу — сюрприз, його
  напрям і сила.
- **Скринінг S&P 500** — воронка Tier A → B → C і композитний скор.
- **Крипто-скринінг ф'ючерсів** — лонг / шорт / спостереження, ширше
  за watchlist.
- **Синтез рішення по ставці ЦБ** — п'ять входів (макро + наші
  прогнози + дохідності й спред 2s10s + новини + виступи членів
  комітету) → `hold` / `cut` / `hike`.
- **Сесійний синтез ринку** — тричі на добу, за часом відкриття
  азіатської, європейської та американської сесій.
- **Пошук новачків** — активи з рухом угору або вниз, яких ще немає в
  наших списках. Це список **спостереження**, не торгів.
- **Список для торгів** — фільтр за каталізатором поверх скринінгів.
- **Розгорнутий аналіз активів** за чинниками кожного
  (`config.py: ASSET_FACTORS`).

### Звітує

Усе йде в Telegram. Кожна джоба має однойменну команду бота — тобто
будь-який звіт можна запросити вручну, не чекаючи розкладу:
`/notify_screening`, `/notify_watchlist`, `/daily_digest`, `/help`.
Watchlist редагується теж із Telegram: `/watchlist_add BNB`,
`/watchlist_remove gbpusd`, `/watchlist_list`.

## Принципи роботи

Це не стиль, а правила, які вже зловили конкретні збої. Порушення
кожного колись коштувало втрачених даних або хибних висновків —
обґрунтування й живі кейси в [docs/decisions.md](docs/decisions.md).

### 1. «Збір» і «аналіз» — завжди окремі шари

`data-ingestion/` лише дістає й нормалізує сирі дані; жодної
інтерпретації чи прогнозування. `analysis/` не парсить джерела.
Завдяки цьому аналітику можна міняти, не чіпаючи джерела, і навпаки.

### 2. Кожне джерело — окремий адаптер з однаковим інтерфейсом

Кастомного парсингу в коді аналізу не буває ніколи.

### 3. Правда — це **згода кількох джерел**, а не офіційність одного

Найдорожче правило. FRED — першоджерело — віддавав Brent за **135.51**
проти справжніх **102.25** (розбіжність 33%), і обидва наші контролі
казали «все гаразд»: `freshness.py` і `quality.py` відповідають на
питання про **час**, не про **правильність**. Хибне значення було
свіже. Тому:

- звірка джерел — `data-ingestion/common/consensus.py`;
- FRED викинуто з ланцюжків резервування: механізм обирав за
  **свіжістю**, а брехливі значення були свіжі;
- для звірки критично брати **той самий різновид ряду** — `CUSR0000SA0`
  (сезонно згладжений) проти `CPIAUCSL`, а не `CUUR0000SA0`: інакше шар
  звірки давав би хибну тривогу щодня й знецінився б.

### 4. Сирі зібрані дані не видаляються ніколи

`raw_observations` — append-only назавжди: нова ревізія старого факту
це теж `INSERT`. На цій історії тримається якість майбутніх прогнозів
(~300 точок на показник; повторний збір із нуля її **не** відтворить —
FRED/ECB віддають глибину, Binance і Twelve Data ні).

**Єдиний виняток — `raw_news`:** обґрунтування правила стосується
макропоказників, а стаття тижневої давності прогноз не покращує. Збір
обмежено 24г, зберігання 48г.

### 5. Кожен LLM-виклик логується

Промпт + відповідь + час + джерело → `llm_call_log`, і кожен висновок
посилається на свій рядок. Без цього неможливо постфактум зрозуміти,
чому агент сказав саме це.

### 6. Watchlist-ціни — завжди на сьогодні, без штучних затримок

Для «поточної ціни» береться джерело з **найчастішим реальним
оновленням**, а не «офіційне, але повільне». Якщо одне джерело не дає
активу або дає застаріле — пробується наступне, а не «ну, джерело ж
є». Свіжість **перевіряється** (дата останньої точки проти сьогодні),
а не припускається. Показник, місячний **за природою** (ВВП, CPI), під
це правило не підпадає — то цикл релізу, не поганий вибір джерела.

### 7. Контроль коректності — властивість системи, не ручна робота

Перш ніж вважати актив або нове джерело готовим, система сама
перевіряє: чи значення збігається з незалежним джерелом, чи його не
переписують заднім числом, чи досить історії для розрахунків на ньому.
Не «чекаємо, поки людина помітить і попросить виправити».

### 8. Дефект тут майже ніколи не падає з трасуванням

Головний висновок із усієї розробки. Він тихо повертає `False`,
порожній список або константу — **і виглядає як робочий код**.
Приклади, знайдені **виміром**, а не читанням:

| Що виглядало робочим | Що робило насправді |
|---|---|
| `catalyst_score` | не різнив активи: глобальний реліз важив більше за власну новину активу |
| прапорець ревізій | спрацьовував завжди (8 з 11 активів) — порівнював рядки однієї дати, не зважаючи на час забирання |
| ранжування «за підтвердженістю» | `cluster_count = 8` у ВСІХ рядках — ранжувало однакові числа |
| детектор аномалій | читав хардкод замість живого списку джерел → ряд із 6 точок → завжди `False` |
| дедуп циклу релізу | ламався на часових поясах: японський реліз 08:30 JST = 23:30 UTC попереднього дня |
| гейт конвеєра релізів | один рядок `impact='low'` тримав його відкритим вічно — 10 080 холостих прогонів на добу |

**Практичний висновок:** будь-яку правку аналітики перевіряти **живими
даними з БД**, і міряти **до** та **після**. Усі шість дефектів вище
знайдено виміром виводу. Цей же принцип вбудовано і в
`scripts/backup_db.sh` — він звіряє кількість рядків у резерві з
живою базою й падає при розбіжності, бо саме так зловив власний
дефект: `pg_dump` по hypertable `raw_observations` віддавав порожнього
батька, і «успішний» резерв містив 0 рядків замість 340 тисяч.

## Стек

- **Python 3.12** — уся логіка
- **PostgreSQL 16 + TimescaleDB** — одна база для часових рядів і
  реляційних даних; `raw_observations` — hypertable
- **APScheduler** — окремий сервіс `scheduler`, без Celery/Airflow
  (зайва інфраструктура для незалежних періодичних джоб без черг і DAG)
- **Docker Compose** — три сервіси: `db`, `app`, `scheduler`
- **LLM: два провайдери одночасно.** Який виклик куди — у `config.py`,
  розділ `LLM_ROUTES`: Anthropic для прогнозу й висновків, які читає
  людина; DeepSeek для механіки (фільтр релевантності, консолідація,
  дедуп, екстракція тикерів) і як резерв

## Структура

```
config.py            ЄДИНИЙ конфіг: усі пороги, ваги й чек-листи.
                     Жоден модуль не визначає ці значення сам.
data-ingestion/      ЗБІР сирих даних (без аналізу)
  macro/ companies/ quotes/ crypto/ commodities/ reports/ news/
  common/              спільний інтерфейс адаптера, БД, свіжість,
                       якість ревізій, ЗВІРКА ДЖЕРЕЛ, watchlist
analysis/            обробка зібраного
  forecasting/         прогноз + бектест проти naive
  expectations/        факт vs очікування
  news_analysis/       класифікація, агрегація, синтези
  screening/           скринінг акцій S&P 500
  crypto_screening/    скринінг ф'ючерсів
  discovery/           пошук новачків
  trading_list/        список для торгів
  fundamental/         аналіз за чинниками + звітність
  calendar_outlook/    ранковий огляд календаря
monitoring/          календар релізів, тригери, виступи ЦБ, звірка
reporting/           генерація і надсилання звітів у Telegram
orchestration/       розклад і автозапуск (APScheduler)
  schedule.py          ЄДИНИЙ файл для зміни періодичності
db/schema.sql        схема БД — джерело істини
db/backup/           резерв даних (invest_agent_data.sql.gz)
scripts/             розгортання, резерв, відновлення
docs/                що робить кожна джоба, журнал рішень, архітектура
```

Детальний потік даних — [docs/architecture.md](docs/architecture.md).

## Перевірка коду

```bash
docker compose exec app pytest -q
```

**1503 тести.** Вони перевіряють **код**, не наявність даних: на
порожній базі всі пройдуть, а скринінг і синтез нічого не покажуть.
Для перевірки, що працює **система**, — [OPERATIONS.md](OPERATIONS.md),
розділ «Щоденна перевірка живучості».
