# Розгортання

Як підняти агента з нуля на ноуті або сервері. Два шляхи:

| Шлях | Коли | Час |
|---|---|---|
| **А. З резерву БД** (рекомендовано) | звичайний випадок — у репозиторії є `db/backup/` | **~10 хв** |
| **Б. З порожньої бази** | резерву немає або потрібна свідомо чиста історія | **~1.5 год** |

Різниця принципова. Історію спостережень **не можна перезібрати
повністю**: FRED і ECB віддають глибину, а Binance, Twelve Data і
Yahoo — лише останні дні. Шлях Б дасть агента, який працює, але з
короткими рядами — а прогнозування тримається саме на глибині (~300
точок на показник).

## Вимоги

### Залізо

| | Мінімум | Комфортно |
|---|---|---|
| RAM | 2 ГБ | 4 ГБ |
| Диск | 5 ГБ | 10 ГБ |
| CPU | 1 ядро | 2 ядра |

База займає ~300 МБ одразу після відновлення й росте приблизно на
**150–250 МБ за місяць** (переважно `raw_observations` і
`llm_call_log`). Логи самоочищаються через 14 днів, новини — через 48
годин.

Інтернет потрібен постійно: агент увесь час тягне дані з зовнішніх
API.

### Docker — тільки нативний Engine, НЕ Docker Desktop

```bash
sudo apt install docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo usermod -aG docker $USER   # щоб не писати sudo; потім перезайти в сесію
```

**Чому саме так.** Docker Desktop — навіть версія для Linux — підіймає
контейнери у власній легкій ВМ, і bind mount (`.:/app` у
`docker-compose.yml`, яким код потрапляє в контейнер) синхронізується з
хостом **не миттєво**. Живо підтверджено: редагування файлу на хості
інколи не доходило до контейнера без `docker compose restart app`, а
`apply_schema.py` молча застосовував **застарілу схему**. На голому
Docker Engine bind mount — пряме спільне використання файлової
системи, без цього класу проблем.

Перевірка:

```bash
docker compose version
```

### Ключі API

| Змінна | Обов'язково | Де взяти | Безкоштовно |
|---|---|---|---|
| `DB_PASSWORD` | **так** | придумати будь-який | — |
| `FRED_API_KEY` | так (макро США) | [fred.stlouisfed.org](https://fred.stlouisfed.org/docs/api/api_key.html) | так |
| `TWELVEDATA_API_KEY` | так (ціни акцій) | [twelvedata.com](https://twelvedata.com/) | так, ~8 запит/хв |
| `SEC_EDGAR_USER_AGENT` | так (фундаментал) | просто `назва контакт@email` | так |
| `DEEPSEEK_API_KEY` | так (механіка ШІ) | [platform.deepseek.com](https://platform.deepseek.com/) | платно, дешево |
| `ANTHROPIC_API_KEY` | так (прогноз, висновки) | [console.anthropic.com](https://console.anthropic.com/) | платно |
| `TELEGRAM_BOT_TOKEN` | для звітів | [@BotFather](https://t.me/BotFather) | так |
| `TELEGRAM_CHAT_ID` | для звітів | [@userinfobot](https://t.me/userinfobot) | так |
| `ESTAT_APP_ID` | для CPI Японії | [e-stat.go.jp](https://www.e-stat.go.jp) | так |

ECB, BOJ, Binance, CoinGecko, Bybit, OKX, GDELT і всі RSS — **без
ключів**, публічні ендпоінти.

Без `TELEGRAM_*` агент працює й пише в базу, але звітів ви не
побачите. Без `ANTHROPIC_API_KEY` прогноз і людські висновки
недоступні — як аварійний режим можна перевести все на DeepSeek
(`SYNTHESIS_LLM_PROVIDER=deepseek`), це важіль на випадок аварії, не
спосіб налаштування.

## Шлях А. З резерву БД (~10 хв)

### Крок 1. Клонувати

```bash
git clone <URL-цього-репозиторію> ai-invest-agent && cd ai-invest-agent
```

Перевірити, що резерв на місці (має бути ~13 МБ):

```bash
ls -lh db/backup/invest_agent_data.sql.gz
```

### Крок 2. Заповнити `.env`

```bash
cp .env.example .env && nano .env
```

`DB_PASSWORD` обов'язковий — без нього контейнер бази **не
підніметься** (це навмисно). Решта — за таблицею вище; `.env.example`
містить коментар до кожної змінної.

`.env` у `.gitignore` і ніколи не комітиться.

### Крок 3. Підняти контейнери

```bash
docker compose up -d --build
```

Перший білд — 2–4 хвилини (ставляться Python-залежності). Піднімаються
три сервіси:

| Сервіс | Що робить |
|---|---|
| `db` | PostgreSQL 16 + TimescaleDB, порт тільки на `127.0.0.1` |
| `app` | контейнер із кодом; `sleep infinity`, для ручних команд |
| `scheduler` | APScheduler — виконує 48 джоб, `restart: unless-stopped` |

Перевірити:

```bash
docker compose ps
```

Усі три мусять бути `running`, `db` — ще й `(healthy)`.

### Крок 4. Відновити базу з резерву

```bash
bash scripts/restore_db.sh
```

Скрипт сам: дочекається готовності бази → перевірить, що вона порожня
→ застосує схему (`db/schema.sql`) → завантажить дані → **звірить, що
лягло**, і покаже цілісність посилань.

Очікуваний вигляд кінцівки:

```
✅ Відновлено. Що в базі:

         t         |  rows  | from_date  |   to_date
-------------------+--------+------------+------------
 raw_observations  | 340795 | 1951-07-01 | 2026-10-13
 sources           |     36 |            |
 watchlist_assets  |     12 |            |
 backtest_verdicts |     71 |            |
 ...

Цілісність посилань (мусить бути 0 у кожному рядку):
 raw_observations→sources            | 0
 результати→llm_call_log             | 0
 expectation_synthesis→comparisons   | 0
```

Якщо `raw_observations` = 0 або в цілісності не нулі — **не
продовжуйте**, дивіться [TROUBLESHOOTING.md](TROUBLESHOOTING.md),
розділ «Відновлення бази».

> Скрипт накладає резерв **тільки на чисту базу** і падає на
> наповненій. Це навмисно: резерв містить `COPY`, а не upsert — тихо
> подвоїти історію спостережень гірше, ніж впасти.

### Крок 5. Перевірити код

```bash
docker compose exec app pytest -q
```

Очікується **1374 passed**. Ключі для цього не потрібні — тести
перевіряють код і не торкаються ні мережі, ні бази, тож проходять і
на незаповненому `.env`. Якщо падають —
[TROUBLESHOOTING.md](TROUBLESHOOTING.md).

### Крок 6. Зареєструвати Telegram-команди

```bash
docker compose exec app python orchestration/register_telegram_commands.py
```

Наповнює «/»-меню бота назвами й описами всіх 48 джоб. Разова дія
(повторити лише після додавання нової джоби).

### Крок 7. Засіяти календар релізів

```bash
docker compose exec app python orchestration/run_job.py refresh_calendar
```

**Не пропускайте.** Без цього `release_log` лишається порожнім аж до
першого запланованого прогону (понеділок 6:00), а до того весь
ланцюжок факт/очікування на свіжому розгортанні просто нічого не
робить — це була справжня діра, знайдена живим розгортанням.

### Крок 8. Переконатися, що планувальник узявся до роботи

```bash
docker compose logs --tail 60 scheduler
```

У логах мусить бути перелік 48 джоб із часом наступного запуску.

Перший живий звіт — найближчою Telegram-джобою за розкладом. Не чекати:

```bash
docker compose exec app python orchestration/run_job.py notify_watchlist
```

Прийшло повідомлення в Telegram — **розгортання завершено**.

### Після відновлення

**Усі 48 джоб уже працюють** — агент повноцінний, нічого доналаштовувати
не треба. Переконатися:

```bash
docker compose exec app python orchestration/run_job.py --list   # 48 рядків
docker compose logs scheduler | grep -c "Added job"              # 48
```

Що саме робить кожна з 48 — [docs/jobs.md](docs/jobs.md), згруповано за
обіцянками агента. Короткий огляд напрямків — [README.md](README.md),
розділ «Що агент робить».

#### Єдине, що в резерві застаріле

Таблиця нижче — **не** перелік функціоналу, а вичерпний список того,
що резерв НЕ несе або несе зліпком. Решта 43 джоби тут відсутні саме
тому, що їхні дані в резерв увійшли й застарілими не є (скринінг,
синтези, список для торгів, кандидати, фундаментальний аналіз,
вердикти бектесту — усе на місці з першої хвилини).

| Що | Чому застаріле | Коли освіжиться само |
|---|---|---|
| новини (`raw_news`) | у резерв не входять навмисно — живуть 48г за дизайном | протягом 2 годин (`news_collect_rss`) |
| ціни watchlist | зліпок на момент резерву | 6:00 і 17:00 |
| ціни S&P 500 | зліпок | 3:00 |
| скринінг | рахується на цінах, тож перерахується після них | 5:00 |
| календар релізів | майбутні дати відносні до дня резерву | понеділок 6:00, або крок 7 вручну |

Тобто максимум за добу агент сам приходить у повністю свіжий стан.
Хочете не чекати — `bash scripts/bootstrap_2_pipeline.sh` прогонить
конвеєр один раз негайно (~15–30 хв, витрачає LLM-кредити).

## Шлях Б. З порожньої бази (~1.5 год)

Кроки 1–3 і 5–8 ті самі. Замість кроку 4 (відновлення):

### Крок 4а. Застосувати схему

```bash
docker compose exec app python data-ingestion/apply_schema.py
```

### Крок 4б. Масовий backfill

```bash
bash scripts/bootstrap_1_backfill.sh
```

**~1 година**, здебільшого через ліміт Twelve Data (8 запитів/хв на
~500 тикерів S&P 500). Скрипт сам чекає на реальне завершення всіх
трьох паралельних зборів (ціни universe, фундаментал SEC EDGAR,
глибша історія макро) і друкує ✅/❌ по кожному — термінал зайнятий
увесь час.

У фоні, не тримаючи сесію відкритою:

```bash
nohup bash scripts/bootstrap_1_backfill.sh > logs/bootstrap_run.log 2>&1 &
```

Прогрес: `tail -f logs/bootstrap_*.log`

### Крок 4в. Прогнати конвеєр один раз

Коли скрипт надрукував «Усі три backfill'и завершились успішно»:

```bash
bash scripts/bootstrap_2_pipeline.sh
```

Прогонить увесь ланцюжок (календар → скринінг → новини → ціни →
класифікація → синтез → дайджест) через `orchestration/run_job.py` —
той самий код, що потім виконує планувальник.

**Чому це окремий обов'язковий крок:** звичайний щоденний розклад
розрахований на систему, де масові backfill'и колись уже відбулись. На
щойно піднятій системі скринінг і LLM-синтез молча не працюють, доки
їх не пройдено — про це легко забути, бо нічого не падає.

> Після шляху Б історія буде коротка (дні, не роки). Прогнозування
> перейде на naive там, де не вистачає точок для бектесту. Це
> виправляється часом — або резервом із іншої машини.

## Автозапуск при перезавантаженні машини

Сервіси вже мають `restart: unless-stopped` — Docker підніме їх сам
після рестарту демона. Щоб вони вставали і після **перезавантаження
ОС**, треба лише щоб сам Docker був у автозапуску:

```bash
sudo systemctl enable docker
```

Нічого більше (ні cron, ні systemd-юніта для агента) не потрібно:
планувальник живе всередині контейнера `scheduler`.

## Headless-сервер / VPS

Працює без змін — усе через `docker compose`, графічного середовища не
потрібно. Два моменти:

**1. База вже не виставлена в інтернет.** У `docker-compose.yml` порт
прив'язаний саме до `127.0.0.1`, не до `0.0.0.0`. Без цього префікса
Docker публікує порт на **всіх** інтерфейсах і сам додає правило в
iptables, яке проходить «поверх» ufw/firewalld — база опинилася б
доступною з інтернету. Не змінюйте цей рядок.

**2. Часовий пояс.** Розклад читається в `Europe/Kyiv`. Якщо сервер в
іншому поясі — це не проблема (контейнери отримують `TZ` зі змінної),
але якщо хочете інший пояс розкладу, задайте `SCHEDULER_TIMEZONE` у
`.env`.

Доступ до бази з ноута через SSH-тунель, не відкриваючи порт:

```bash
ssh -L 5432:127.0.0.1:5432 user@сервер
```

## Оновлення до нової версії

Повна процедура — по одній команді за раз, щоб на кожному кроці було
видно результат. Виконувати з теки, куди клоновано цей репозиторій.

### 1. Резерв перед оновленням

```bash
bash scripts/backup_db.sh ~/backup-before-update.sql.gz
```

Єдиний крок, який не можна пропустити: дані (`raw_observations`) —
незамінні, код завжди можна відкотити через `git`.

### 2. Забрати нову версію

```bash
git pull
```

### 3. Перезапустити з новим кодом

```bash
docker compose up -d --build
```

Код монтується в контейнер як volume, тож формально ребілд обовʼязковий
**лише** коли змінився `requirements.txt` або `Dockerfile`. Але
`up -d --build` безпечний завжди й гарантує, що **планувальник
перезапустився з новим кодом** — без цього `scheduler` і далі крутить
старий (він запускає джоби як підпроцеси, але сам процес `main.py`
живе в памʼяті з моменту старту).

### 4. Застосувати схему

```bash
docker compose exec app python data-ingestion/apply_schema.py
```

Безпечно повторювати: усі `CREATE` — з `IF NOT EXISTS`, усі `INSERT` —
з `ON CONFLICT DO NOTHING`.

### 5. Перевірити код

```bash
docker compose exec app pytest -q
```

Очікувано: `1374 passed` за ~10-15 секунд.

> **Якщо оновлюєтесь із версії до 2026-10-15** — зверніть увагу:
> раніше цей самий `pytest` **виконував пʼять джоб по-справжньому**.
> Гейт перевірки імпортів запускає кожен скрипт-джобу з `--help`,
> розраховуючи, що argparse вийде до `main()`; у пʼяти скриптів
> argparse не було, тож вони виконувались цілком — із викликами LLM,
> записами в БД і **надсиланням повідомлень у Telegram**. Саме так це
> й знайшлося: прогін тестів на відновленій базі надіслав огляд
> календаря. Виправлено; ознака, що нова версія справді стала —
> `pytest` триває секунди, а не хвилину-дві.

### 6. Переконатися, що планувальник узявся до роботи

```bash
docker compose logs --tail 20 scheduler
```

У лозі має бути свіжий рядок про зареєстровані джоби, а далі —
`scheduler_heartbeat` кожні 5 хвилин. Пряма перевірка пульсу:

```bash
docker compose exec db psql -U invest_agent -d invest_agent -c \
  "select last_tick_at, now() - last_tick_at as age from scheduler_heartbeat"
```

`age` більше 10 хвилин означає, що планувальник не працює — далі
[TROUBLESHOOTING.md](TROUBLESHOOTING.md).

### 7. Прогнати одну джобу вручну

```bash
docker compose exec app python orchestration/run_job.py crypto_screening_daily
```

Остання перевірка — тим самим кодом і образом, що й за розкладом.
Будь-яку іншу джобу видно в `orchestration/run_job.py --list`.

### Якщо щось пішло не так

```bash
git log --oneline -5
```

Відкотитись на попередній коміт і перезапустити:

```bash
git checkout <попередній-хеш> && docker compose up -d --build
```

Дані при цьому не торкаються — вони в томі БД, не в коді. Якщо
постраждали саме дані, відновлюйте з резерву кроку 1:
`bash scripts/restore_db.sh ~/backup-before-update.sql.gz` (потрібна
ЧИСТА база — скрипт сам про це скаже).
